# Generated application services

Capability `application.services` owns per-entity application data and scheduled jobs. Agent private memory and the authoritative world ledger are separate namespaces and never bound to generated Workers.

The dispatcher chooses `APP_DATA.getByName(entityId)` from the validated hostname and creates the `ctx.exports.ApplicationDataConnector` loopback service with server-owned entity props, then passes that serializable service stub through `ctx.props.APP_DATA`. A local `RpcTarget` cannot be serialized through dynamic dispatch arguments. The connector wraps `ScopedApplicationData`; this target exposes get/put/delete without an entity argument. It hides the namespace and scheduler methods. Records are UTF-8 strings bounded to 32,000 characters, with 1,000 keys per entity. Writes enforce quota within a Durable Object transaction. These are application records: generated code can deliberately return its own data publicly, so do not store private goals, memory or credentials there.

`site/services.json` declares up to ten jobs with intervals of 5–1,440 minutes and reserved local paths. The publication pipeline validates and retains the manifest with its deployment ID. The trusted execution cron dispatches only the active ledger deployment, adds `ctx.props.job`, and passes the same scoped data target. Public dispatch rejects `/_arti/*`; callers cannot supply job props in HTTP headers. Published template code demonstrates a persistent refresh timestamp and status API.

Each scheduled tick claims a durable key before invoking generated code. Duplicate events do not repeat execution. A crash after claiming requires operator investigation; jobs are at most once per tick, and are not a general exactly-once transaction across code and storage. Old claims expire after seven days. The scheduler ignores disabled or paused worlds and rechecks deployment identity before dispatch. Already dispatched work may finish during a concurrent pause.

Both production and staging dispatch bindings use `arti-generated-outbound`, a deny-all outbound Worker. Generated code receives no raw Durable Object namespace, account token, private service binding or mTLS binding. Cloudflare outbound Workers block socket connect as well as intercepting fetch. Deploy the outbound Worker before execution. This first policy grants no external generated-service access; expanding it requires operator-reviewed allowlists and resource accounting.

Verification: `pnpm exec vitest run apps/execution/features/application-services`, then `pnpm exec vitest run --config apps/execution/vitest.workers.config.ts`. The runtime tests check persistence across eviction, cross-entity isolation, hidden scheduler authority, safe keys and concurrent quota enforcement.

A cumulative 1 MB serialized application-record allowance bounds backup size in addition to the per-record and key-count limits. Backups freeze this entity's store before reading app records and scheduled-job claims. Writes check both world permission and the local freeze flag inside their transaction. App snapshots are private R2 objects with SHA-256 references in the complete backup manifest. Restore verifies the checksum and record schema before replacing data, preserves the freeze through partial failure, and requires an explicit world-authorized release after the world has resumed.

Loopback regression coverage passes the connector through real WorkerEntrypoint props and checks persistent writes and cross-entity isolation. Dynamic dispatch and scheduled invocations both create a fresh connector per request; never cache its RPC stub across requests.
