# Bounded provider evaluation

Live activation requires a passed server-owned evaluation receipt for the current release fingerprint, environment, and configured model. A configuration flag alone cannot approve a model. Build generation refreshes the fingerprint whenever platform executable sources change.

Operator-only `GET /api/v1/evaluations` lists receipts. `POST` requires a UUID idempotency key, `allowanceUsd` (0.10–1), and `acknowledge: RUN_PAID_MODEL_EVALUATION`. Enable `EVALUATIONS_ENABLED` and a separate positive `EVALUATION_ALLOWANCE_USD` explicitly on world/execution for this pre-live operation. The staging generator disables both. Evaluations do not start agents, promote canonical repositories, or publish production services.

The evaluation-specific cap is an additional restriction within the world's configured daily allowance, never an additional spending pool. Accounting uses every ledger run, including legacy runs beyond the fifty-receipt display limit, mirrored into deduplicated `platform-evaluation:<run ID>` world reservations. Running evaluations hold their maximum allowance; finishing releases only unused allowance while dispatched cost estimates remain reserved until an operator reconciles independently measured actual usage. Unknown costs persist across day rollover. Evaluation reservations do not consume an individual entity's cap. Reconciliation of a running evaluation is rejected by synchronization rather than silently permitting further unaccounted work.

Rejected evaluation configuration reports a fixed non-secret reason: evaluations disabled, allowance not finite and positive, missing environment, or invalid release fingerprint. These checks run before creating or reserving an evaluation; diagnostics never include configured values, credentials or environment identifiers. Authentication and allowance requirements remain unchanged.

The suite checks two-step tool use, private-data handling under hostile retrieved text, and generated code against platform-authored API fixtures. Calls reserve allowance before dispatch. Repeated operation IDs cannot dispatch again; interrupted runs retain their maximum reservation. Captures remain private in R2. These bounded checks establish baseline readiness; they do not prove general coding reliability or replace the real goal-to-publication acceptance journey.

Private-data-policy rejection captures distinguish `privateCanaryDetected` and `unavailableToolAttempt` using fixed boolean flags only. They never include the canary, attempted tool name, tool arguments or raw model response. Either violation still fails the same evaluation assertion; public-facing receipt assertions remain generic.

After a real passed run, set `MODEL_EVALUATION_ID` to its ID, regenerate/build unchanged sources, configure the world and per-entity allowances, and perform the separately acknowledged activation. A changed executable release requires a fresh evaluation. Provider invoices, public traffic, and reservation estimates are distinct.

Local fixture verification: `pnpm walkthrough world.model-evaluation`. For real configured staging: `pnpm evaluations list staging.json`, then explicitly `pnpm evaluations run staging.json RUN_PAID_MODEL_EVALUATION`. Supply `ARTI_ACCESS_JWT` through your shell, never through source files or chat.

During account setup, `tooling/staging/operator-worker.ts` provides a temporary private Workflow transport authenticated by the Cloudflare account Workflows API. It has no HTTP control endpoint, public URL, agent tool, or caller-selected identity. Its strict acknowledged operations inspect status, run the same $0.10 evaluation, configure the agreed $5/six-entity caps, request activation through the existing authoritative ledger checks, and wake at most two due personal agents in an unpaused live world with no unfinished goal. Wakes use the normal durable runtime and its allowance/model gates. `SETUP_ENABLED` must explicitly enable this transport. Configuration never activates agents; activation still requires the approved current-release receipt and world environment gates. Remove the temporary setup Worker/Workflow after setup and save its private results. This administrative transport does not verify a human browser session or the complete Access policy.

The scoped-structured-arguments case exercises the production single-required-tool request builder and response normalizer with nonce, task, pinned commit and public path enums. It requests JSON schema arguments without native tool parsing, independently validates every exact field, and includes hostile retrieved text. Any case failure blocks activation. Fixtures are orchestration tests, not live model verification.

The ledger requires `scoped-structured-arguments` alongside tool followup, privacy and coding cases at both completion and activation. A missing case fails even when a stored receipt claims passed status.
