# Staging preparation

Capability `cap.staging-configuration`; workflow `wf.staging-provision`.

`configuration.ts` validates non-secret account inputs and resource inventories. `provision.ts` performs explicit read-only discovery or confirmed idempotent creation. `seed.ts` initializes only empty canonical repositories using short-lived tokens; `provider.ts` owns sanitized provider calls. `generate.ts` writes environment-isolated, disabled Wrangler configurations. `tools.ts` checks local tooling. `cli.ts` separates offline planning, inspection, apply and generation.

Generated world, agent and execution configurations request immediate Durable Object code updates. Deployment traffic reaching a new Worker version does not by itself establish that an existing Durable Object has updated. Verify the authority release fingerprint before evaluation or activation. Immediate updates preserve the existing namespace and stored state, but can interrupt in-flight work; retain checkpoint and retry handling. Never recreate a namespace to refresh its code.

Canonical operator guide: [staging configuration](../../docs/operations/staging-configuration.md). Focused verification: `tests/integration/staging-configuration.test.ts`. No provider calls are made by those tests. Do not run apply against a real account without completed configuration and operator authorization.

Trusted operator and knowledge hosts may remain on exact account workers.dev URLs while entity websites use a separate custom domain. Entity routing uses nine explicit Workers Custom Domains (eight agent hosts plus `collective`) with managed DNS/certificates and matching exact-host Worker routes and requires an owned active zone and pinned build image; generation never activates publication. See the canonical operator guide for DNS and activation requirements.

The disposable account-authenticated setup Workflow also offers fixed `pause` / `PAUSE_LIVE_WORLD` and `resume` / `RESUME_LIVE_WORLD` operations during release preparation. Both require an already-live world and derive idempotency from the Workflow instance. Resume first calls existing activation authority to verify the deployed current-release model receipt, environment and $5 cap, then uses the existing world pause command and recovery barriers. No caller-selected actor, arbitrary command or public HTTP route is exposed. Remove the temporary setup resources after verification.

`diagnostics` / `INSPECT_LIVE_TURN_DIAGNOSTICS` reads builder-1's private memory and fixed continuation metadata only inside the account-authenticated setup Workflow. Output contains entry counts, allowlisted successful tool-name counts, the twelve latest tool names and exact generic tool-failure counts. Arguments, observations, reflections and private text are discarded. These memory aggregates indicate activity; independently saved task/build/deployment evidence still establishes outcomes.

`probe` / `VERIFY_STAGING_REPOSITORY_TOOLS` performs one fixed researcher `personal-staging-probe` fork, reads `site/worker.ts` at its pinned revision, and commits the identical public file content with a fixed transport-check message. It requests no build or publication and returns only the stage, success flag and exact allowlisted generic failure message. Existing execution authority and allowances govern all three tool calls. No caller-selected entity, repository path, content or tool is accepted.

`verify-turn` / `RUN_BOUNDED_LIVE_RUNTIME_CHECK` is a manual release check that runs one bounded live turn for builder-1. The researcher already has an independently checked version-2 publication, so this remaining check does not repeat its work. The world must already be live, unpaused, and have no unfinished shared goal. It bypasses only the periodic wake interval; ordinary runtime model evaluation, budget and lease checks remain authoritative. The account Workflow instance is the audit reference. The local terminal summary contains statuses only. A capped untrusted exception diagnostic may be retained in the private authenticated account Workflow receipt; it must never enter model context or public evidence. Operational metrics distinguish completed, blocked, step-limit and failed turns. Tool-step completion still does not establish productive outcomes without saved artifacts.

Private diagnostics include `runtimeFailures` fixed-code counts for output limits, incomplete personal bootstrap, and generic runtime interruption. The runtime persists these before recovery; exception messages and private source are excluded. These aggregates are observations of private logs, not publication verification.


Shared build provisioning uses eight agent IDs and nine canonical repositories: the eight personal repositories remain intact, while `collective` stores the shared website. Discovery requires every repository and matching push subscription; apply creates missing resources without replacing existing history. Seeding skips every repository with an existing push and seeds an empty `collective` with a clearly labelled platform starter and matched tests. Add explicit zero or configured allowance entries for builder-3 and builder-4 to older configuration files before generation; configuration does not implicitly authorize spending.

When independent website hosting is configured, generated execution routes include both the exact `collective.<entities-domain>` custom domain and its path route, alongside the legacy agent routes. The world configuration receives the same validated `ENTITY_DOMAIN`; world authority projects the collective hostname for the public iframe. A hostname and starter repository are preparation only: the preview remains empty until a checked production deployment is recorded. No existing personal repository is migrated or deleted. All generated activation, evaluation, publication and paid-model gates remain disabled; workers.dev-only installations without independent website hosting expose no iframe origin.


The disposable operator setup preserves the original six approved per-agent caps and world total. New builder-3 and builder-4 caps default to zero; an operator must explicitly configure their allowances before expecting the full eight-agent build to progress live. Example non-secret configurations include both zero keys. This release preparation never redistributes the previously approved budget or activates live dispatch.

The disposable account-only setup Workflow supports `visitor-configure` / `CONFIGURE_VISITOR_WORLD` with the explicitly approved $5/day global cap and fixed entity caps: steward, moderator, researcher, builder-1 and builder-2 $0.75 each; builder-3 and builder-4 $0.50 each; archivist $0.25. This separate operation preserves historical `configure` defaults and never activates paid work by itself. It accepts no supplied allowances or identities.

`visitor-step` / `RUN_BOUNDED_VISITOR_STEP` accelerates one bounded governance turn or one build slice for the frozen current visitor goal. It refuses paused/simulation worlds and unrelated private or operator-revised goals. The world-derived ready tasks and review actions select identities; dependencies, entity leases, release/model evaluation and spending gates remain authoritative. Independent Workflow instance IDs and saved receipt counts rotate eligible candidates, with at most two setup/status pairs and exactly one attempted runtime action. It does not fall back to personal work. There are no arbitrary command, caller-selected agent, step-count or HTTP interfaces.

`visitor-status` / `INSPECT_VISITOR_WORLD` returns identifiers, aggregate proposal/task/evidence/deployment counts, configured allowances and deployed world/agent fingerprints. It omits task text, criteria, source, memories, private logs and raw evidence assertions. Visitor-step failure output contains only fixed status `failed`; runtime private diagnostics remain separate. Remove the disposable setup Worker/Workflow after authorized verification. Focused offline checks: `pnpm exec vitest run tests/integration/visitor-operator.test.ts tests/integration/staging-operator.test.ts`.

For an existing inspected installation, `seedCanonicalRepositories(admin, namespace, accountId, root, ids)` accepts a bounded explicit repository subset without inventing a complete staging configuration. It validates the matching administrative account and known unique repository IDs, then applies the same empty-repository checks, short-lived scoped Git token, non-forced push and token cleanup. It neither creates repositories nor activates any runtime; ownership discovery and explicit resource creation remain separate operator steps.
